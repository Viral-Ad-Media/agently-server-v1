Cost, Pricing & Billing

Every paid service Agently depends on, what each one charges us, and exactly how that becomes a number on a tenant's wallet.

Prepared 5 September 2026 Margin 70% gross (3.333× cost) Model Prepaid wallet, pay-as-you-go

This document contains internal cost and margin.

Tenants see a single charge per unit of usage. They never see what a service costs us, nor the multiplier applied. Vendor rates below are published list prices retrieved on 4 September 2026 and are what we pay, not what we charge.

1. How a tenant is billed

Agently is prepaid and usage-based. There is no monthly subscription and no seat fee. A tenant buys credit, and each unit of work draws that credit down as it happens. New accounts start with $5 of free credit; a card must be on file before a phone number can be bought or a chatbot put live, so the account cannot run up cost and walk away.

The pricing formula

tenant charge = our cost ÷ (1 − 0.70) = our cost × 3.333

70% is gross margin, not a 70% uplift. A service that costs us $1.00 is charged at $3.33, of which $2.33 is gross profit. The margin is stored in billing_platform_settings.default_target_margin_percent and is adjustable from the admin panel; the same 100 ÷ (100 − margin) form is used everywhere so per-event and periodic charges can never disagree.

Two kinds of cost

Kind What it is How the tenant pays for it
Direct Metered per tenant by the vendor: a call minute, a synthesised character, a token. Attributable to one tenant with certainty. Charged immediately, as the event happens. The wallet is debited within the same request that logs the usage.
Shared Flat bills that arrive regardless of tenant activity: the Lightsail container services, the Supabase plan. No per-tenant figure exists. Never billed as a line item. It is a cost of doing business, priced into the unit rate. See section 4.

Why infrastructure is not billed separately.

It was built both ways and measured. Apportioning the flat server bill across tenants and charging it at 3.33× produced a $78.89 monthly infrastructure charge for the busiest tenant, in a month where every tenant combined consumed $17.67 of actual provider cost. Infrastructure would have been 78% of the bill.

Vapi, Bland and Twilio all absorb infrastructure into the per-unit price; none of them itemise a customer's share of their servers. Agently now does the same. The apportionment engine still runs — it is what tells us whether the unit rate is high enough (section 4).

Read this number carefully.

Token counts above are illustrative — they are a plausible shape for a five-minute call, not a measurement. Real consumption varies with how much the caller talks, model choice, and whether ElevenLabs or the realtime model produces the audio. The rates are published vendor prices; the quantities must be read off billing_usage_events for real calls before this table is used to set customer-facing expectations.

The practical implication: a $5 free-credit account can make roughly one five-minute realtime call before needing to top up. If the trial is meant to feel more generous than that, the lever is either a cheaper model for trial accounts (gpt-realtime-mini is ~3× less) or a larger grant via BILLING_SIGNUP_GRANT_USD.

The apportionment algorithm

Infrastructure is not billed to tenants, but it is still measured per tenant. That measurement is what proves the unit rate is high enough, and it is what a per-customer profitability question gets answered with.

Splitting a shared bill by one single metric would be a guess — split by call minutes and a chat-only tenant with a large knowledge base contributes nothing to the database they fill. So each bill is attributed by the usage that actually drives that bill:

BillAttributed byWhy
Lightsail 100% compute seconds Containers running websocket audio. Time spent processing a live session is what consumes them.
Supabase 60% stored bytes
40% activity (USD of work)		 The plan is roughly compute against disk and egress, so the split follows that shape.
tenant's share of a bill = Σ (driver weight × tenant's share of that driver)

Four properties the algorithm guarantees, each covered by a test:

  • The split always sums to 100%. No cost silently disappears between tenants.
  • A driver nobody used redistributes its weight. If no tenant stored anything this period, storage's 60% flows to the remaining drivers rather than dropping real cost on the floor.
  • Idle tenants attract nothing. Share is measured in magnitude of work, not row counts — a tenant who sent one email is attributed $0.00, not a slice of the server bill.
  • Cost nobody can be attributed is reported, not hidden. If nothing happened all period, the whole bill shows as absorbed rather than as a misleading zero.

The loss guard

Absorbing infrastructure creates one specific danger: the unit rate looks like it carries a 70% margin while the flat server bill quietly eats it, and nothing on any invoice would reveal that. Every cycle therefore computes:

FigureMeaning
True costprovider cost + infrastructure cost
Revenuewhat tenants were actually charged
Actual marginmargin after infrastructure, not the headline 70%
Break-even multipliermultiple of provider cost at which we stop losing money
Required multipliermultiple needed to hit the target margin with infrastructure absorbed — this is the number that should set unit prices

Current reading: we are running at a loss.

Measured against live data for the 30 days to 5 September 2026, at $37 Lightsail + $10 Supabase:

Provider cost, all tenants$17.67
Infrastructure cost$46.36
True cost$64.03
Revenue at the current 3.333×$58.91
Gross profit−$5.12

Actual margin is −8.69%, not 70%. Infrastructure is 72.4% of what we spend. Break-even is 3.623× provider cost; we charge 3.333×.

This is a volume problem, not a rate problem. $47/month of fixed cost divided by very little usage dominates everything. The same 3.333× rate is comfortably profitable once usage grows — at roughly $650/month of provider cost it yields about 68% actual margin, with infrastructure falling to under 7% of spend. The two levers are growing usage or trimming the container scale; raising the rate to the arithmetic 12× that would force 70% margin at today's volume is not a real option.

If a dedicated customer ever needs it

The engine keeps a passthrough mode that bills each tenant their apportioned infrastructure share directly. It is off, and it should stay off for self-serve customers; it exists for a large dedicated deployment where the customer expects to see infrastructure itemised. Set it with BILLING_INFRA_MODE=passthrough.

5. Current status

Off  The billing engine is not running on a schedule.

In absorb mode it never charges anyone, so the risk of enabling it is reporting noise rather than a wrong invoice. It is still off until deliberately switched on:

#StepStatus
1 Apply migrations/billing_period_charges.sql (the audit table) Not applied
2 Set AWS_LIGHTSAIL_MONTHLY_USD=37 and SUPABASE_MONTHLY_USD=10 (verified, section 4) Unset in .env
3 Set BILLING_ENGINE_ENABLED=true and schedule npm run billing:cycle:commit hourly Unset — in absorb mode this only writes audit rows, it charges nobody

Until all three are done the engine reports and charges nothing. Running npm run billing:cycle at any time prints exactly what would be charged, writing nothing.

Every charge is reconstructable.

Each period writes one row per tenant to billing_period_charges holding the raw driver measurements, the per-provider cost breakdown, the apportionment share, the margin used and the multiplier. A disputed charge can be recomputed from first principles months later — a figure alone is not an answer to a customer asking why.
